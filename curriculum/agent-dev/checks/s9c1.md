## 这一章的项目：一份能执行的选型意见

这一章不写代码。把正文「动手练」第 1 题和第 3 题写进 `architecture_note.md`。

**文件里要有两段**

**一、一个单 Agent 就够的反例**（第 1 题）

找一个你最近用模型干过的事，写一句话说明为什么它**不需要多 Agent**。
这句话里要出现下面任意一个说法：

- 「不需要等」——没有多个异步源要同时等；
- 「一次读完」——一份材料读一遍就够；
- 「顺序执行就够了」——步骤之间有先后，但没有谁等谁。

**二、一个具体业务的选型建议**（第 3 题，≤200 字）

- 明确写「单 Agent」或「多 Agent」，不要写「视情况而定」；
- 给 1 个关键理由，落在下面三条之一：
  **职责不可合并** / **能力隔离** / **失败可局部化**；
- 拿一个具体业务举例，比如「客服对话里查订单状态并安抚用户」。

**为什么卡「明确二选一」**

选型意见最常见的废稿是「各有优劣，视情况而定」。这种话在会上没法拍板。
写错也比不写强——至少能拿来讨论边界。

**为什么卡「理由要具体」**

「多 Agent 更先进」「更灵活」不是理由，是形容词。真正能支撑决策的是
「这两件事的失败后果不一样，混在一起没法单独回滚」这种机制层面的判断。

**验收会检查什么**：文件非空、出现「单Agent」或「多Agent」、出现上面任意一条
理由词、去掉空白后不超过 260 个字符（正文要求建议本身 ≤200 字，给了标题余量）。
