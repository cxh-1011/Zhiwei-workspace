# 第 13 章 给 Agent 上三道锁：token、时间、次数

## 这一章要解决什么

你写了个查天气的 Agent，让它“先问用户城市，再调天气 API，最后说人话”。  
结果它卡在第一步：反复问“请问您想查哪个城市？”，用户回了“北京”，它又问一遍，再回“北京”，它还问……  
或者更糟——你忘了加限制，它一口气发了 27 次请求，OpenAI 账户被扣光，还收到封号警告邮件。

这不是模型“不听话”，是它根本没开关。  
你没给它上锁，它就一直跑，直到崩、超时、刷爆 quota、或你手动 Ctrl+C。

这一章就干三件事：  
- 数它吃了多少 token（别让它一顿吃撑）  
- 给它掐个秒表（5 秒不回，直接换人）  
- 它最多只能干 3 轮活（干完交卷，不许赖着）

不是教它“思考”，是教它**守规矩**。

## 核心概念

### token 是它的饭量单位  
它不吃字，吃 token。中文里一个字常是 1~2 个 token，标点、空格、换行全算。  
你喂它 2000 token，它就真只吃这么多——超了，API 直接拒单。  
不数清楚，就像给小孩发零食不限量，吃完吐了你还怪他胃口差。

### timeout 是它的倒计时闹钟  
OpenAI 接口默认不超时。它卡在哪儿，你就等多久。  
设成 5 秒，就是“5 秒内不给我答案，我就当这轮失败，切到下一步”。  
不是让它快点想，是让它**别死等**。

### max_turns 是它的答题卡页数  
Agent 不是单次问答，是一轮轮对话（user → assistant → tool call → assistant…）。  
设成 3 轮，意思是：从你第一句话开始，到它第三次输出结束，就停。  
不是“最多调 3 次 API”，是“最多完成 3 轮交互”。

## 先跑起来

```python
import os
import time
from openai import OpenAI

client = OpenAI(api_key=os.environ.get("OPENAI_API_KEY"))

# 一次请求，带三重限制
try:
    start = time.time()
    response = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[{"role": "user", "content": "用一句话解释什么是 token"}],
        max_tokens=100,        # 硬性截断：最多输出 100 token
        timeout=5,              # 超过 5 秒就抛异常
    )
    duration = time.time() - start
    print(f"✅ 响应成功，耗时 {duration:.2f}s")
    print(f"💬 输出：{response.choices[0].message.content[:50]}...")
    print(f"📊 总 token：{response.usage.total_tokens}")
except Exception as e:
    print(f"❌ 失败：{type(e).__name__} — {e}")
```

运行后你会看到：  
- 成功时：打印响应内容 + 总 token 数（比如 `total_tokens: 68`）  
- 如果你把 `timeout=0.01`，大概率会报 `TimeoutError`  
- 如果你把 `max_tokens=1`，它会输出极短一句（甚至半句话），然后停  

注意：`response.usage.total_tokens` 是这次请求**实际用掉的 token 总数**（含输入+输出），不是你设的 `max_tokens`。

## 动手练

1. **改代码，加 token 计数器**  
   把上面脚本改成：每次请求前打印“当前已用 token：X”，请求后累加 `response.usage.total_tokens`，超 2000 就 `print("⚠️ 达到总 token 上限，停止")` 并退出。  
   ✅ 做完标志：连续跑 3 次，第 3 次输出里有 `⚠️ 达到总 token 上限`。

2. **加 timeout 防卡死**  
   写个循环，让模型反复回答“1+1=？”，每次设 `timeout=0.1`。观察是否稳定报 `TimeoutError`；再改成 `timeout=2`，看是否能正常答出。  
   ✅ 做完标志：两次运行，一次全是 `❌ 失败：TimeoutError`，一次全是 `✅ 响应成功`。

3. **模拟 3 轮限制**  
   不调 API，写个 `for turn in range(3):` 循环，每轮打印 `第 X 轮`，并在第 3 轮后打印 `🏁 到达最大轮次，结束`。  
   ✅ 做完标志：输出正好三行“第 1 轮”“第 2 轮”“第 3 轮”，最后一行是 `🏁...`。

## 自测

<details><summary>Q1：如果我把 max_tokens 设为 50，但 response.usage.total_tokens 显示 120，可能吗？</summary>
不可能。`max_tokens` 是输出长度上限，`total_tokens` 包含输入+输出。输入部分（比如 system prompt + user message）本身就可能超 50。所以 `total_tokens > max_tokens` 很常见，但 `output_tokens > max_tokens` 不会发生。
</details>

<details><summary>Q2：timeout=5 意味着模型必须在 5 秒内“想完答案”吗？</summary>
不是。“想完”是模型内部事，你控制不了。timeout 是指整个 HTTP 请求从发出去到收到完整响应的耗时上限。网络延迟、排队等待、流式响应的首字节时间，都算在内。
</details>

<details><summary>Q3：为什么不能只靠 max_tokens 防刷 API？举一个具体例子。</summary>
因为 max_tokens 只管单次输出长度，不管调用次数。比如你写个死循环：<code>while True: client.chat.completions.create(..., max_tokens=1)</code>，每次只拿 1 个 token，但每秒调 10 次——token 没超，钱和 quota 却飞了。必须配合轮次限制（max_turns）或外部计数器。
</details>

## 下一章为什么是它

这一章你给 Agent 装了三道物理锁：token、time、turn。  
但它现在只会“硬扛”——超了就崩、超了就停、超了就哑火。  
下一章《让它自己认错、喊停、换路》要教它：  
- 看见 token 快超，主动缩句、跳过细节  
- 发现响应慢，改用更轻的模型或缓存  
- 轮次快用完，优先交核心答案，不纠结边角料  
——不是靠你掐脖子，是让它长出自己的刹车片。
