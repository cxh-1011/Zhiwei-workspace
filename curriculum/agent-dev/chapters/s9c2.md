# 第 30 章 多Agent为啥容易翻车

## 这一章要解决什么

你写好两个 Agent：一个查天气，一个写周报。让它俩自己配合——结果卡住、答非所问、花了 8 秒才吐出“今天晴”，还多花了 3 倍 token。

不是模型不行，是**你没看见它们在背后互相扯皮**：  
- A 刚问完“北京温度多少”，B 回一句“好的”，又转头问 A“请确认城市名”；  
- A 觉得 B 没干活，重发一遍问题；B 又回“已查”，其实啥也没查；  
- 俩人来回发了 5 条消息，真正干活的只有 1 行 API 调用。

这一章不讲怎么搭架构，就盯着这三件事：**它为啥慢、为啥乱、为啥贵**。

---

## 核心概念

### 它不是开会，是「传纸条」  
两个 Agent 之间没有共享内存，没有眼神交流。每次通信都得：  
① 把上文打包成 prompt（带历史、带指令、带工具描述）→  
② 发请求 →  
③ 等模型生成 →  
④ 解析输出 →  
⑤ 再拼下一条 prompt……  
**每轮都是完整的一次大模型调用**，不是“内部函数调用”。

### 指令冲突不是 bug，是默认行为  
你让 Agent A “用表格总结数据”，又让 Agent B “用段落描述趋势”。  
A 输出表格后，B 看到的是纯文本表格（比如 `|日期|温度|\n|---|---|\n|1日|25℃|`），它根本不知道这是“表格”，只当是普通字符串。  
它照着自己的指令——“用段落描述”，就把表格当原文重写了一遍：“第一行是日期和温度……”  
→ **不是它故意错，是它压根没收到“这是表格，请保留格式”的指令**。

### 多一次通信 = 多一次 token + 延迟 + 出错点  
一次调用开销 ≈ 输入 prompt token + 输出 token + 网络延迟（通常 0.5–2s）。  
两个 Agent 往返一次，至少 2 轮调用。  
如果中间还要 parse JSON、retry、加思考链……token 和时间就指数级涨。

## 先跑起来

复制这段代码，保存为 `demo_two_agent.py`，运行：

```python
import os, time
from openai import OpenAI
client = OpenAI(api_key=os.environ.get("OPENAI_API_KEY"))

def ask(model, messages):
    t0 = time.time()
    res = client.chat.completions.create(
        model=model,
        messages=messages,
        temperature=0.1,
        max_tokens=64,
        logprobs=False
    )
    dt = time.time() - t0
    tokens = res.usage.total_tokens
    return res.choices[0].message.content.strip(), dt, tokens

# Agent A: 查资料（假装调 API）
a_msg = [{"role": "user", "content": "查上海今天最高气温"}]
a_resp, a_dt, a_tk = ask("gpt-4o-mini", a_msg)
print(f"[A] 耗时 {a_dt:.2f}s | token {a_tk} | 回复：{a_resp}")

# Agent B: 写摘要（接收 A 的结果）
b_msg = [{"role": "user", "content": f"把这句话改写成适合发邮件的语气：{a_resp}"}]
b_resp, b_dt, b_tk = ask("gpt-4o-mini", b_msg)
print(f"[B] 耗时 {b_dt:.2f}s | token {b_tk} | 回复：{b_resp}")

print(f"总耗时 {a_dt+b_dt:.2f}s | 总 token {a_tk+b_tk}")
```

你会看到类似：  
```
[A] 耗时 0.87s | token 42 | 回复：上海今天最高气温为32℃  
[B] 耗时 0.72s | token 38 | 回复：您好，今日上海最高气温为32摄氏度。  
总耗时 1.59s | 总 token 80
```

注意：`a_resp` 是纯文本，直接塞进 `b_msg` —— B 完全不知道自己是在处理“查询结果”，只当是普通句子。

## 动手练

1. **加耗时日志**：修改上面代码，在每次 `ask()` 前后打印 `[A→B] 开始调用` 和 `[A→B] 完成，耗时 Xs`，确保你能一眼看出谁在调谁。  
   ✅ 做完标志：输出里出现两行带 `→` 的耗时标记，且数字和 `time.time()` 计算一致。

2. **加冲突提示**：在 `b_msg` 构造前加一行判断：如果 `a_resp` 包含“℃”或“摄氏度”，但 `b_msg` 的 instruction 里没提“温度单位”，就 print `"⚠️ B 指令未覆盖单位，可能丢失精度"`。  
   ✅ 做完标志：运行时确实打出这行警告。

3. **加发起方标记**：把 `a_msg` 和 `b_msg` 都改成带明确 role 的 list，例如 `a_msg = [{"role": "system", "content": "你是查天气助手"}, {"role": "user", "content": "..."}]`，并确保 `b_msg` 的 system 提示里写明“你只负责润色，不查数据”。  
   ✅ 做完标志：`b_resp` 不再出现“我查到……”这类越界回答。

## 自测

<details><summary>1. 如果把 Agent A 的回复从“32℃”改成“高温预警”，Agent B 的输出很可能变差。为什么？</summary>
因为 B 的 prompt 里只说“改写成邮件语气”，没告诉它“高温预警”是专业术语、不能拆解或解释。模型会按字面猜，可能写出“天气很热，发出警告”这种失真描述。
</details>

<details><summary>2. 下面这行代码有没有问题？`b_msg = [{"role": "user", "content": a_resp}]`</summary>
有问题。它把 A 的原始回复直接当 user 输入扔给 B，没加任何上下文说明。B 不知道这是“查询结果”，也不知道该信还是该验证。正确做法是加 system 角色说明来源，比如 `{"role": "system", "content": "这是天气查询助手返回的原始结果"}`。
</details>

<details><summary>3. 两个 Agent 往返一次，最少触发几次大模型调用？</summary>
2 次。A 生成一次，B 接收 A 的输出后再生成一次。不存在“一次调用完成协作”的捷径。
</details>
