# 第 10 章 二十个工具怎么不选错

## 这一章要解决什么

你给模型塞了 20 个工具：查天气、读文件、改代码、搜 GitHub、调数据库、发邮件、转 Markdown、压缩图片……  
它看着列表，沉默三秒，然后调用了 `send_email`——而你只是想让它把 `main.py` 里第 12 行的 `print` 换成 `logging.info`。

这不是它懒，也不是它叛逆。  
是它根本没看清：**这 20 个按钮里，哪个才是真正该按的那个**。

就像你第一次进厨房，灶台上有 8 个旋钮、5 个开关、3 个抽屉——你得先知道「哪个旋钮控制大火」，才敢点火。

这一章就干一件事：教它看懂每个工具的「一句话身份证」，别认错人。

---

## 核心概念

### 工具描述不是说明书，是“召唤咒语”  
你写 `{"name": "edit_file", "description": "编辑一个 Python 文件"}`，它可能去调 `search_github`——因为“编辑”和“搜索”在它眼里都带点“找东西”的味道。  
真正管用的描述得像一句命令：“**只改指定文件的某一行，不读其他内容，不运行，不保存为新文件**”。  

### 模型不数工具个数，它只比“匹配度”  
它不是从左到右扫一遍列表，选第 7 个。它是把你的请求（比如“把 log 级别从 DEBUG 改成 INFO”）和每个工具的描述一起喂给大模型，让模型打分：“这个描述和这句话像不像？”  
所以两个工具描述太像（比如都写“修改代码”），它就容易摇摆。

### 冗余描述 = 给模型加噪声  
`get_file_content` 和 `read_source_code` 如果都写着“读取代码文件内容”，它俩在模型眼里就是同一个人穿了两件马甲。  
删掉一个，不是少一个工具，是让剩下那个被看见的概率翻倍。

## 先跑起来

```python
import os
from openai import OpenAI

client = OpenAI(api_key=os.environ["OPENAI_API_KEY"])

tools = [
    {
        "type": "function",
        "function": {
            "name": "edit_file",
            "description": "只修改指定文件中某一行的代码；不执行、不保存副本、不读取无关行",
            "parameters": {"type": "object", "properties": {"file_path": {"type": "string"}, "line_number": {"type": "integer"}, "new_content": {"type": "string"}}, "required": ["file_path", "line_number", "new_content"]}
        }
    },
    {
        "type": "function",
        "function": {
            "name": "search_github",
            "description": "在 GitHub 上按关键词搜索公开仓库的 README 或 issue，不 clone、不读源码",
            "parameters": {"type": "object", "properties": {"query": {"type": "string"}}, "required": ["query"]}
        }
    }
]

response = client.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": "把 utils.py 第 5 行的 logging.debug 改成 logging.info"}],
    tools=tools,
    tool_choice="auto"
)

print("选中的工具名：", response.choices[0].message.tool_calls[0].function.name)
```

✅ 跑完你会看到输出：`选中的工具名： edit_file`  
如果它选了 `search_github`，说明描述还不够锋利——回去改 `edit_file` 的 description，加更狠的限定词，比如“**必须精确到行号，且不涉及任何网络请求**”。

## 动手练

1. **改描述**：把你本地 `tools.json` 里的 `run_python_script` 描述，从“运行一个 Python 脚本”改成一句带限制的命令。  
   ✅ 做完标准：改完后，输入“检查 config.py 语法是否正确”，它不再调 `run_python_script`（而是该调 `check_syntax`）。

2. **造干扰项**：在工具列表里加一个新工具 `parse_python_code`，描述写成“分析 Python 代码结构”。然后给模型发请求：“把 main.py 第 3 行缩进加 4 个空格”。  
   ✅ 做完标准：它仍选 `edit_file`，而不是 `parse_python_code`。如果选错了，说明两个描述边界不够清，删掉或重写 `parse_python_code` 的描述。

3. **测召回率**：准备 10 个真实请求（如“生成 requirements.txt”、“查 pandas 最新版本号”），用你当前的 20 个工具跑一遍。  
   ✅ 做完标准：至少 8 个请求选对唯一工具（`tool_calls` 长度为 1，且 name 正确）；记录下哪两个错了，直接删掉对应工具的描述，重跑。

## 自测

<details><summary>Q1：为什么把工具描述写成“可以做 A，也能做 B，有时还顺手做 C”反而会让模型更难选？</summary>
因为它不是在找“能用的”，是在找“最贴切的”。描述越宽，和其他工具的得分就越接近，模型就越容易随机选一个。
</details>

<details><summary>Q2：以下两个工具描述，哪个更容易让模型区分？为什么？<br>A. “读取文件内容”<br>B. “只读取文件前 100 字符，不解析、不编码转换、不报错”</summary>
B 更容易区分。A 和十几个工具（read_json、load_config、parse_csv…）语义重叠；B 用三个“不”划出清晰边界，几乎没有其他工具敢这么写。
</details>

<details><summary>Q3：调用时 `tool_choice="required"` 和 `"auto"` 的区别，会影响模型选工具吗？</summary>
不影响“选哪个”，只影响“要不要选”。`"required"` 强制必须选一个（哪怕瞎选），`"auto"` 允许它不选（返回普通文本）。选错是描述问题，不是 choice 设置问题。
</details>
