# 第 16 章 哪些事该记进长期记忆里

## 这一章要解决什么

你让模型帮你查资料，它翻完文档，回你一句“已记下”。  
你隔两天问“上次说的 API 怎么用”，它眨眨眼：“哪个 API？”

不是它装傻。是它根本没“记”——每次请求都是新开始，上一句和下一句之间，**没有内存，只有上下文**。

这一章就干一件实在事：**教它在哪儿存、怎么找、什么时候掏出来用**。  
不是靠它“记得住”，而是你帮它建个抽屉，贴好标签，再教它开门的手势。

比如你总让它改同一段代码逻辑，它每次都重读；  
比如你反复告诉它“公司禁用 requests 库”，它下次还用；  
比如你让它查完某个接口文档，下次聊“登录流程”时，它该自动把那段文档甩出来——而不是等你再说一遍。

这些事，不该靠模型“记住”，而该由你决定：**哪些信息值得存，存在哪，怎么让它自己想起来**。

---

## 核心概念

### 1. 长期记忆 ≠ 模型的记忆  
模型没有硬盘。所谓“长期记忆”，是你在外部建的数据库（哪怕只是个 JSON 文件），每次调用前，你挑几条 relevant 的塞进 `messages` 里。  
它不记得你，但你能让它“看起来记得”。

### 2. 存什么？看它是不是“反复出现、影响决策、无法临时推导”  
- ✅ 用户常忘的密码/账号（不能靠推理，必须存）  
- ✅ 你定的硬规则（如“所有代码必须用 httpx”）  
- ✅ 它查过一次的结构化结果（如“/api/v1/login 返回字段：token, expires_in”）  
- ❌ “今天天气不错”（不相关）、“我叫小王”（太泛，没用途标记）  

### 3. 什么时候取？别等它问，你来判断  
不是用户说“帮我回忆”，而是你看到关键词（如“登录”“密码”“API”），就主动从记忆里捞出匹配项，拼进 prompt。  
**触发靠你，不在模型里写 if-else。**

## 先跑起来

```python
import json
import os
from datetime import datetime
from openai import OpenAI

client = OpenAI(api_key=os.environ.get("OPENAI_API_KEY"))

# 模拟一条记忆：用户常忘密码，用于登录场景
memory_item = {
    "id": "mem_001",
    "content": "公司登录密码是 P@ssw0rd-Dev2024",
    "timestamp": datetime.now().isoformat(),
    "usage": ["login", "password", "reset"]
}

# 存成文件（真实项目里可换 SQLite 或向量库）
with open("memories.jsonl", "a") as f:
    f.write(json.dumps(memory_item, ensure_ascii=False) + "\n")

# 下次聊“登录”时，我们手动读出来用
with open("memories.jsonl", "r") as f:
    for line in f:
        mem = json.loads(line.strip())
        if "login" in mem["usage"]:
            print("✅ 自动取出记忆：", mem["content"])
            # 实际中，你会把 mem["content"] 加进 messages[0] 或 system message
```

运行后你会看到：  
`✅ 自动取出记忆： 公司登录密码是 P@ssw0rd-Dev2024`  
——它没“想起来”，是你看到 `login` 就把它翻出来了。

   ✅ 做完：运行后输出那句 black 规则。

## 自测

<details><summary>1. 如果我把 memory 的 usage 写成 ["login"]，但用户输入是 "怎么登系统？"，为什么可能匹配失败？</summary>
因为匹配是字符串包含（in），不是语义相似。“登系统”不含字符串 "login"。你需要要么统一用中文标签（如 ["登录"]），要么加简单关键词映射（如把“登系统”→“登录”）。纯靠模型理解关键词会不可控。
</details>

<details><summary>2. 以下代码有没有问题？</summary>
```python
mem = {"content": "xxx", "usage": "login"}  # 注意：usage 是 str，不是 list
if "login" in mem["usage"]: ...
```
有问题。`mem["usage"]` 是字符串 `"login"`，`"login" in "login"` 为 True，看似能过，但一旦想加多个用途（如 `"login, password"`），就会错乱。必须用 list：`"login" in mem["usage"]` 才安全。
</details>

<details><summary>3. 判断正误：只要把记忆条目加进 system message，模型就一定能用上。</summary>
错误。加进去只是给了它看，但它可能忽略、混淆、或被长上下文冲掉重点。真正可靠的是：控制输入长度 + 把最相关的 1–3 条放在 user message 开头 + 必要时用 tool call 显式唤起。
</details>

## 下一章为什么是它

这一章你只存了、也只手动拿了。  
但真实场景里，“登录”可能出现在用户第 5 句话，也可能藏在“我登不上那个后台”里。  
下一章《用向量快速找记忆》，就教你：不用关键词硬匹配，而是把用户这句话转成向量，去记忆库找“最像”的几条——比如“登不上后台”自动连上“登录密码”。
