# 第 33 章 靠用户反馈改出下一版

## 这一章要解决什么

你发了个“帮我看下这段 Python 有没有 bug”，它回了 200 字分析，还加了改法——用户却回：“我要的是直接改好代码，不是写作文。”

你心里一紧：是不是模型太弱？是不是 prompt 写错了？是不是该换家 API？

先别急着调 temperature。  
**用户那句吐槽，才是你下一个版本最准的测试用例。**  
但问题来了：ta 说“太啰嗦”，是真的嫌字多，还是根本没看懂？说“不准”，是逻辑错、事实错，还是压根没读你的代码？说“卡”，是等了 8 秒，还是点了 3 次都没反应？

这一章就干一件事：把用户发来的每一条语音转文字、微信截图、飞书留言，变成你能马上动手改的清单。

---

## 核心概念

### 1. 反馈 ≠ 问题，而是线索  
用户说“结果不对”，不是让你修模型，是告诉你：“我在用这个功能时，遇到了一个和预期不符的结果”。  
你要做的是还原场景：ta 输了什么？模型回了什么？ta 期望的又是什么？三者对齐，才能定位是 prompt 漏了约束、tool call 传错了参数，还是根本没调 search 工具。

### 2. 三类问题，对应三种改法  
- **功能缺失**：比如用户要“查 PEP 8 规范里缩进怎么写”，你没接文档检索工具 → 下版必须加 tool。  
- **回答错误**：比如用户问“requests.get() 的 timeout 参数单位是秒还是毫秒？”，它答“毫秒” → 是知识错，得加 reference 或限制幻觉。  
- **太慢**：比如点“帮我重写函数”后卡住 5 秒才动 → 不是模型慢，是你的代码在等一个没超时的 HTTP 请求 → 加 timeout=3 和重试。

### 3. 优先级 = 影响人数 × 痛点强度  
一条反馈说“重试按钮没有”，但如果 7 个人都提了，且每人卡住超过 3 次，这就是下周必须上线的按钮；  
另一条说“希望支持 Markdown 表格”，只有 1 人提，且当前输出已能看 → 先记 backlog，不排期。

## 先跑起来

```python
import os
import pandas as pd

# 假设你导出了前 10 条用户反馈（从飞书/微信/日志里复制粘贴）
feedbacks = [
    "每次改代码都要手动复制粘贴，累死了",
    "问 Python 装包命令，它说 pip install -r req.txt，但我要的是 pip install xxx",
    "点‘运行’后转圈 10 秒，我以为挂了",
    "解释太多，我只要改好的代码",
    "查不到我本地的 README.md 文件",
    "说‘根据文档’，但我没给它任何文档",
    "重试按钮在哪？我想再试一次",
    "返回的代码有语法错误，exec 报错",
    "能不能把输出框变大一点？",
    "问‘怎么用 asyncio.gather’，它讲了一堆原理，没给例子",
]

df = pd.DataFrame({
    "原始反馈": feedbacks,
    "分类": ["", "", "", "", "", "", "", "", "", ""],
    "优先级": ["", "", "", "", "", "", "", "", "", ""]
})
print(df)
```

运行后你会看到一个空表格。下一步就是手动填：  
- 第 1 行，“手动复制粘贴” → 功能缺失（缺一键插入）→ 高优先级（多人提过）  
- 第 2 行，“pip install -r” → 回答错误（混淆了命令场景）→ 高  
- 第 3 行，“转圈 10 秒” → 太慢（缺 loading 提示 + 超时）→ 高  
……  
填完你就有了第一份可执行的迭代清单。

## 动手练

1. **归类练习**：从你自己的项目里找 5 条真实用户反馈（哪怕只有 2 条也行），按「功能缺失 / 回答错误 / 太慢」三类填进上面的表格。  
　✅ 做完标准：表格里每行都有明确分类，无“其他”项。

2. **优先级标定**：对这 5 条，按“是否多人重复提 + 是否阻断主流程”打分（高/中/低）。  
　✅ 做完标准：至少 2 条标为“高”，且理由能对应到具体行为（如：“3 人说卡住，且都发生在点击运行后”）。

3. **写需求**：挑出 1 条“高”优先级反馈，写出下版要改的 1 条具体需求（必须含动词+对象+约束）。  
　✅ 做完标准：需求像这样：“加一个‘重试’按钮，位置在输出框右上角，点击后重新执行上次请求，不刷新页面”。

## 自测

1. 用户反馈：“回答太快了，感觉没想清楚”。这属于哪一类问题？  
<details><summary>参考答案</summary>
不属于三类中的任何一类——这是错判。用户不是在说响应快，是在质疑质量（大概率是回答错误或幻觉）。需回溯原始输入和输出，不能只看情绪词。</details>

2. 为什么不能直接把“希望加 dark mode”标为高优先级？  
<details><summary>参考答案</summary>
因为没满足“影响人数 × 痛点强度”：如果只有 1 人提，且当前功能完全可用，就不构成阻断性问题。优先级要看是否让核心流程走不下去。</details>

3. 如果 8 条反馈都指向“查不到本地文件”，但你的系统本来就没设计文件读取能力，这时第一步该做什么？  
<details><summary>参考答案</summary>
不是立刻写代码，而是确认需求真伪：查日志，看这 8 条反馈是否都发生在同一类操作（如都点了“分析我的项目”按钮）；如果是，说明用户预期你有该能力——那这就是明确的功能缺失，要排期加 tool，而不是怪用户“不会用”。</details>

这一章你学会了从吐槽里挖需求，但光有清单不够——

没有这一章的归类，下一章的训练数据就是一堆乱码。
