# 第 29 章 多智能体真有用吗

## 这一章要解决什么

你让模型帮你改代码，它改得能跑；你让它查资料再写周报，它真能凑出一页带引用的文档。这时候很容易想：「再加个Agent专门做校验」「再拆一个Agent专管调API」——好像多叫几个人，活就干得更稳。

这一章不讲怎么搭多Agent，先问一句：**它真的需要好几个人一起干吗？**

很多同学一上来就画三个Agent互相发消息，结果发现：两个Agent之间传的全是废话，第三个Agent根本没用上，最后还不如一个Agent从头做到尾。

我们直接看真实场景：什么时候非得喊帮手？什么时候只是自己吓自己？

---

## 核心概念

### 1. 「职责不可合并」才是多Agent的硬门槛  
不是「功能多」就要拆，是「同一时刻必须同时做几件互斥的事」。比如：一个Agent在等数据库返回（卡住），另一个却要实时听用户语音输入——它们不能串行，必须并行。单Agent做不到这点。

### 2. 「能力隔离」比「分工」更重要  
不是「A写代码、B查文档」就该拆。而是当A的能力（比如写Python）和B的能力（比如调企业内网API）**根本没法装进同一个模型提示词里**——要么超长，要么冲突，要么安全策略禁止混用。这时拆开才真有用。

### 3. 「失败可局部化」是多Agent的隐藏好处  
一个Agent崩了，别让它拖垮全局。比如：负责调外部天气API的Agent挂了，至少文档生成Agent还能用缓存数据继续写报告。单Agent一崩全停。

## 先跑起来

```python
import os
from openai import OpenAI
client = OpenAI(api_key=os.environ.get("OPENAI_API_KEY"))

# 单Agent：一次性完成「读代码 → 改bug → 写注释」
response = client.chat.completions.create(
    model="gpt-4o",
    messages=[
        {"role": "user", "content": "这段Python有bug：def add(a, b): return a + b + 1。请修复它，并给函数加一行中文注释。"}
    ],
    temperature=0.2,
)
print(response.choices[0].message.content)
```

运行后你会看到：一段修复后的代码 + 一行注释，一气呵成。  
注意：没有中间步骤、没有状态保存、没有「先修再注」的显式分步——它靠的是上下文连贯性，不是靠多个角色协作。

## 动手练

1. **找反例**：找一个你最近用模型干过的事（比如「把Excel转成SQL建表语句」），写一句话说明为什么这事**单Agent就能搞定**（提示：看它是否需要同时等待多个异步源）。  
   ✅ 做完标准：这句话里出现「不需要等」「一次读完」「顺序执行就够了」中任意一个。

2. **画对比图**：用文字草图（不用画图工具）画出「单Agent查资料+写报告」vs「Agent A查资料、Agent B写报告」的流程。标出数据流向和等待点。  
   ✅ 做完标准：单Agent图只有1个方框；双Agent图有2个方框+1条带箭头的线，且线上标着「等待A返回结果」。

3. **写选型建议**：选一个具体业务（比如「客服对话中自动查订单状态并安抚用户」），写一段≤200字的技术选型建议，说明该上单Agent还是多Agent，并给出1个关键理由。  
   ✅ 做完标准：字数≤200；明确写了「单Agent」或「多Agent」；理由直指「职责不可合并」「能力隔离」或「失败可局部化」中的一个。

## 自测

<details><summary>1. 判断：「让模型一边听用户语音，一边查知识库，一边生成回复」必须用多Agent。</summary>
错。OpenAI的语音转文本（Whisper）和文本生成（Chat）是分开API，但整个流程仍是串行：语音→文本→查库→生成。只要不需「语音还在收，查库已开始」这种真并行，单Agent协调就行。
</details>

<details><summary>2. 为什么「用一个Agent调10个不同权限的内部API」不如拆成多个Agent？</summary>
因为每个API可能要求不同身份凭证、不同网络策略、不同错误重试逻辑。把这些混在一个提示词里，会超长、易冲突、难调试，也违反最小权限原则——这是「能力隔离」的典型需求。
</details>

<details><summary>3. 如果多Agent系统里某个Agent总返回空字符串，但其他Agent照常工作，这说明什么？</summary>
说明失败被局部化了——问题被限制在那个Agent内部，没污染全局状态或阻塞其他流程。这是多Agent架构的实际收益之一。
</details>
