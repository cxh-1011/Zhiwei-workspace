问题不在于「答得不好」，而在于答完就散了：每次对话都从零开始， 读过的、想通的、决定过的，都没有留下来。

02
为什么要改

聊天机器人 vs. 个人工作空间

现在的形态：问答机器

  • 每次对话从零开始
  • 用户自己决定记什么
  • 用完即走，没有沉淀
  • 价值 = 单次回答质量

目标形态：研究资产库

  • 用得越久越懂你手上的东西
  • 助手参与维护档案状态
  • 每次使用留下可复用资产
  • 价值 = 时间上的复利

缺的那一环很小，但很关键：助手只能读记忆、只能读任务，不能写。 所以档案永远是用户一个人在填。

03
核心设计

权限门做在「工具注册层」，不在「提示词层」

做法机制可靠性
提示词层 在系统提示词里写「请不要自动写入」 软约束 模型可能不遵守，也无法验证
工具注册层 关闭时三个写入工具根本不进入 tool schema 硬约束 模型看不到，就没有任何调用途径

我用了拦截请求的方式验证：关闭时，发给模型的 schema 里确实不含这三个工具； 打开后才出现。这个属性有自动化测试兜底。

04
实现

三个写入工具

工具作用关键约束
remember 写入一条长期记忆 内容相同不重复写；上限 1200 字符；来源标记为 agent
list_learning_tasks 列出计划与任务编号、完成状态 只读。勾选前必须先调它取 plan_id / task_id
set_task_status 把任务标记为完成 / 未完成 两个编号必须匹配，否则返回失败并提示先查列表

注意后两个是刻意的两跳结构：模型必须先查再改。 它把「模型会不会瞎猜编号」变成了一个可观测、可统计的失败模式。

07
可追溯

给写权限，就得给「审计」手段

# 兼容旧库的增量迁移
_ensure_column(cursor, "memories",
               "source", "TEXT DEFAULT 'user'")

def _ensure_column(cursor, table, column, ddl):
    existing = {row[1] for row in
        cursor.execute("PRAGMA table_info(%s)" % table)}
    if column not in existing:
        cursor.execute("ALTER TABLE %s ADD COLUMN %s %s"
                       % (table, column, ddl))

先查再改，幂等；重启自动执行，不需要手工改库。

用户能看到的

  • 学习档案里，助手写的那条带 助手写入 标签
  • 对话的「过程展示」里能看到每一步工具调用与参数
  • 随时可以单条删除，不影响用户自己写的
  • 原有 1 条记忆完好，source 自动补为 user

实测

用真实模型跑过的四个场景

输入模型行为轮数说明
「请帮我记住：我在研究多轮工具调用」 调用 remember 2 改写成了陈述句后落库
「你好，今天心情不错」 未调用任何工具 1 没有过度调用
「把第一项未完成任务标记为完成」 list_learning_tasks → set_task_status 3 两跳正确，没瞎猜编号
同样要求记住，但开关关闭 未调用任何工具 1 工具未注册，写不进去

10
边界

这套方案目前的局限

问题具体表现
写入时机靠模型判断 「什么时候该写」仍由模型理解用户意图决定，提示词只能约束不能保证；极端情况下可能漏写或多写
记忆检索不分相关性 上下文用的是最近 20 条记忆，不是最相关的 20 条；记忆变多后早期重要信息会被挤掉
没有用户隔离 memories 表没有 user_id，单人使用没问题，多用户会互相看到
线上尚未部署 改动目前只在本机验证通过，服务器上还是旧版本，需要上传后重启

下一步

接下来做三件事

A

引用溯源

论文回答带上页码与原文片段，能回查、能给出处。成本最低，用户价值最直接。

B

评测集

30 条覆盖六类场景的小评测集，把「工具选对没有」变成可统计的指标，也是研究工作的基础设施。

C

记忆相关性召回

把记忆从「按时间取最近 20 条」改成「按相关性召回」，一个改动同时提升对话和任务规划。

一句话：先让系统可靠地留下东西，再测量它留得好不好。

附录

导师可能会问的问题

模型会不会乱写、污染档案？
写权限默认关闭，关闭时工具根本不注册；开启后也要求用户明确提出，且写入来源标记为 agent、可单条删除。三道防线：注册层、提示词、可审计。
这和只改 prompt 有什么区别？
prompt 是软约束，模型可能不遵守；不注册的工具模型看不到，属于硬约束。我用拦截请求验证过 schema 里确实没有这些工具。
为什么不用向量检索记忆？
当前记忆量级是几十条，取最近 20 条够用；相关性召回已列入下一步。它的收益在记忆变多以后才显现。
怎么证明它「真的有用」？
目前是功能级验证（61 项检查 + 四场景实测）。效果级证明需要评测集，这是下一步要补的短板。
模型调用失败怎么办？
工具异常统一返回失败而不是抛出，让模型有机会换策略；同时有轮数、单轮工具数、总耗时、token 四重预算上限。
这些改动会破坏已有数据吗？
不会。迁移只新增一列并有默认值，重启自动执行；实测原有记忆完好，source 自动补为 user。
