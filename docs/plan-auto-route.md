# 自动选功能：不再让用户先点三个卡

## 一句话

首页原来要依次回答「你要用智能对话、文件问答还是论文助手」，现在直接打字就行。
系统按这句话判断该走哪条链路，判断结果露在消息下面，点一下就能改。

对应代码：`backend/router.py`（规则）、`POST /route`、`frontend/app.js` 的
`resolveRoute()` / `askForMaterial()`。

## 为什么可以自动

三类功能的区别不在「用户想干什么」，而在「有没有材料」：

| 材料状态 | 该走哪条 | 例子 |
|---|---|---|
| 什么都没传 | 智能对话 | 「ReAct 是什么」 |
| 传了文件/图片 | 文件问答 | 「这张图里是什么」「总结一下」 |
| 解析过 PDF，且问题是问这一篇 | 论文助手 | 「这篇论文的方法部分」 |
| 句式指向材料，但还没传 | 先提示上传，不发送 | 「附件里的第三条」 |

「先提示上传」是关键：把「这张图里是什么」直接发进聊天，模型只能回一句
「我看不到图片」，用户得把问题再说一遍。提示一次、传完再发，省掉这一轮。

## 为什么用规则，不调模型分类

- 三类意图的词面差异足够大，规则能给出确定答案；
- 零延迟、零成本、可单测；
- 模型分类会在边界上飘：同一句话今天判文件、明天判闲聊，用户会觉得网站时好时坏。

代价是词表要手写（`router.py` 顶部四组词），换课程/换功能时要跟着改。
这比让一个概率模型决定「要不要读文件」更容易解释，也更容易修。

## 四条边界

1. **「帮我写论文」不是「读这篇论文」。** `PAPER_OFFTOPIC` 把写作、排版、查重、
   找文献挡在论文助手之外，否则会先要求他上传一份并不存在的 PDF。
2. **已经选了 PDF，就不再要求解析。** 文件问答本身能读 PDF，论文助手要的是索引；
   为了读一份 PDF 让他传两遍，是没有必要的摩擦。
3. **写作/检索类问题不套文件口吻。** 没有材料、也没有指代词时一律按普通对话，
   不让「Python 列表怎么去重」被要求「先添加资料」。
4. **手动永远优先。** 模式栏可以随时切回某个功能；自动判断只作用于 `auto` 模式。
   判断结果以小字挂在用户消息下面（如「自动 · 文件问答 · 已经选了资料」），
   判错了点一下就能改。

## 状态与失败

- 没测过/判断不出：按普通对话，`reason` 说明「没提到具体材料」。
- `/route` 挂了：前端兜底为「有文件走文件问答，否则普通对话」，不拦着用户提问。
- 缺材料：只提示 + 打开文件选择框，输入内容保留，不发出去；
  补完材料后再发同一句，按刚才那一类处理（`pendingMaterial`），不会因为
  「总结一下」没有指代词又被判回普通对话。

- `test_router.py` 42 项全过（离线，不联网）。

- 真浏览器（Edge headless，`backups/ui_smoke/probe_route.py`）30 项：
  首页可直接输入、模式栏显示自动、三种问法的路由结果、缺文件/缺论文只提示不发送、
  输入内容保留、手动覆盖、新建对话回到自动、发送请求里 `mode`/`filename` 正确。

## 已知限制

- 词表是手写的。「帮我找几篇 RAG 的论文」会被判成普通对话（这是有意的），
  但更绕的说法可能判错；错一次点一下模式栏即可。
- 判断只看这句话和材料状态，不看附件内容。上传了一份周报却问「这个方法可行吗」，
  会被当成普通对话——指代词（「这份报告里」）才是可靠信号。
- 附件判断依赖前端传来的 `has_file`，它只认「已上传且在选择列表里」，
  选了个本地文件还没上传时不会被当成有材料。
